# Budget and Event Services Unit Test Plan

## 1. Purpose

This plan defines the unit tests contributed by the Budget and Event services
to the single project-wide testing dossier requested by the instructor.

The instructor requires at least one test for every important business method,
including nominal and boundary/error cases. These tests therefore focus on the
public methods of `BudgetService`, `DepenseService`, and `EvenementService`.

These unit tests are separate from the existing Spring Boot integration tests.
They must isolate one service class at a time, must not start the Spring
context, and must not connect to H2, PostgreSQL, or Supabase.

## 2. Scope and Test Count

| Service | Unit under test | Public methods | Planned unit tests |
|---|---|---:|---:|
| Budget | `BudgetService` | 5 | 14 |
| Budget | `DepenseService` | 4 | 9 |
| Event | `EvenementService` | 5 | 13 |
| **Total** | **3 service classes** | **14** | **36** |

The existing 28 Budget integration tests and 6 Event integration tests remain
useful regression tests, but they are not counted as the 36 unit tests above.

The following are intentionally outside the unit-test scope:

- Controllers, because their HTTP behavior is already exercised by integration tests.
- Spring Data repository implementations, because they are generated by Spring Data.
- DTO validation annotations, because invalid request data is already covered by integration tests.
- Constructors, getters, simple mapping records, and private methods tested indirectly through public behavior.
- Real database and real inter-service calls.

## 3. Tools and Conventions

- Java 21
- JUnit 5
- Mockito
- AssertJ and JUnit assertions
- Maven Surefire for execution reports
- Arrange, Act, Assert structure
- Test names that describe the expected behavior

Service tests use `@ExtendWith(MockitoExtension.class)`, `@Mock`, and
`@InjectMocks`. Repository and external-service dependencies are mocked.

| Test class | Unit under test | Mocked dependencies |
|---|---|---|
| `BudgetServiceTest` | `BudgetService` | `BudgetRepository`, `DepenseRepository`, `EventValidationPort` |
| `DepenseServiceTest` | `DepenseService` | `BudgetRepository`, `DepenseRepository` |
| `EvenementServiceTest` | `EvenementService` | `EvenementRepository`, `OrganisateurValidationPort` |

|---|---|---|

| ID | Scenario | Expected result |
|---|---|---|
| `UT-BUD-08` | Update an existing budget amount | Amount changes while ID and event association remain unchanged |
| `UT-BUD-09` | Update a missing budget | `BudgetNotFoundException` |

### Financial report

| ID | Scenario | Expected result |
|---|---|---|
| `UT-BUD-10` | Calculate a report without expenses | Total expenses is zero, balance equals the budget, and no overspending is reported |

| `UT-BUD-13` | Expenses exceed the budget | Remaining balance is negative and `depassement` is `true` |

## 7. Required Mockito Verifications

Tests verify both returned results and dependency interactions when those
interactions express a business rule:

- Event validation happens before Budget creation.
- Organizer validation happens before Event creation.
- Missing related resources never cause a save.
- Duplicate budgets never cause a save.
- Missing budgets never query or save expenses.
- Missing expenses and events never call update or delete persistence methods.
- Financial aggregation is requested only after the budget is found.
- Expense update never replaces its existing budget association.
- Event listing calls the filtered or unfiltered repository method as appropriate.
- Event deletion translates a persistence constraint failure into `EvenementInUseException`.
- `BigDecimal` values are compared numerically with `isEqualByComparingTo`, not `equals`.

## 8. Implementation and Commit Order

Implement and verify one business service at a time:

1. Add the 14 `BudgetServiceTest` scenarios and run them independently.
2. Add the 9 `DepenseServiceTest` scenarios and run them independently.
3. Run all Budget unit and integration tests.
4. Add the 13 `EvenementServiceTest` scenarios and run them independently.
5. Run all Event unit and integration tests.
6. Save the real Surefire results for the shared dossier.

Suggested progressive commits:

```text
test(budget): add budget service unit tests
test(budget): add expense service unit tests
test(events): add event service unit tests
```

For the single project-wide dossier, provide:

- All 14 important public business methods have nominal and meaningful boundary/error coverage.
- All repositories and external services are mocked in unit tests.
- Unit tests run without Spring, a web server, or a database.
- All 36 planned unit tests pass on Java 21.
- Both complete existing integration-test suites still pass.
- Dossier totals exactly match the generated Surefire reports.
